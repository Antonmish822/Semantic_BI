# Обзор грамматики CCCR (v2.4) для разработчиков движка

Язык CCCR (Context-Compute-Construct-Recursive) представляет собой декларативный JSON-ориентированный DSL маппинга. Его цель — рекурсивный обход исходных данных, вычисление значений (через встроенные запросы) и их трансляция в RDF-триплеты.
Ниже приведен детальный анализ структуры грамматики для реализации синтаксического анализатора (парсера) и AST.

[Собственно грамматика языка CCCR (в BNF)](http://a.roz37.ru/lipers/%D1%81%D0%B5%D0%BC%D0%B0%D0%BD%D1%82%D0%B8%D1%87%D0%B5%D1%81%D0%BA%D0%B8%D0%B9.%D0%BA%D0%BE%D0%BD%D1%82%D1%80%D0%B0%D0%BA%D1%82/%D0%BC%D0%B8%D1%81%D0%B8%D1%81/cccr/%D0%B3%D1%80%D0%B0%D0%BC%D0%BC%D0%B0%D1%82%D0%B8%D0%BA%D0%B0/%D0%B2%D0%B5%D1%80%D1%81%D0%B8%D1%8F-2.4)

## 1. Топология структуры (Корневые сущности)

Схема CCCR всегда начинается с корневого объекта `description`:

* `CCCR`: Обертка вида `{"description": { ... }}`.
* `Description`: Основной блок контекста. Конструкция может содержать три необязательных узла: `Context`, `About` и `Properties`.
* `Properties`: Массив объектов типа Property.

## 2. Структура Property и рекурсия

Элемент `Property` — это точка ветвления графа. Он объявляется как JSON-объект:
$$\text{Property} \to \text{QName} + [\text{Context}]? + (\text{URI} \mid \text{Literal} \mid \text{Description})$$
Рекурсивный шаг: Если третьим аргументом Property является не терминальный литерал/URI, а вложенный `Description`, движок обязан породить новый изолированный контекст вычислений, уходя вглубь структуры.

## 3. Механизм контекста и псевдопеременных (Context)

`Context` отвечает за локальное состояние выполнения:

* `PredicatesList`: Задает массив строк-предикатов или вычисляемое выражение. Движок должен итеративно применять текущие инструкции к каждому предикату из данного списка.
* `PseudoVariable`: Пары `Name : Value` (где значение — литерал либо динамический `computedExpression`). Это локальные переменные («стейт»), доступные для вложенных вычислений.

## 4. Семантика идентификаторов объектов (About и QName)

* `About`: Отвечает за определение URI субъекта (`rdf:about`) для текущего `Description`. Может быть жестко захардкожен (`Literal`) или вычисляться на лету (`computedExpression`).
* `QName`: Квалифицированное имя свойства (предиката). Состоит из строгого разделения на nameSpace (URI пространства имен) и `PrefixedName` (локальное имя с префиксом).

## 5. Вычислительный слой (computedExpression)

Самый критичный узел для реализации бэкенда движка. Любое динамическое значение оборачивается в блок "compute". Движок обязан поддерживать три типа исполнителей (`Evaluators`):

   1. `xquery`: Выполняет XQuery-выражения над исходным XML/HTML документом. Может принимать одиночное выражение, массив из двух выражений или внешнюю вставку (`include`).
   2. `sparql`: Выполняет SPARQL-запросы к семантическому графу. Может принимать опциональный Context для проброса переменных внутрь запроса.
   3. `include`: Механизм переиспользования кода и подгрузки внешних схем/модулей по их URI.
