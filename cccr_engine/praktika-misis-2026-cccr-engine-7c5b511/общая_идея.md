# Общее представление языка CCCR для разработки движка

Основная цель движка CCCR: автоматизация десериализации слабоструктурированных бесконтекстных данных (например, древовидных XML/HTML структур, CSV или классических реляционных таблиц) и их трансформация в семантически обогащенный формат RDF (граф триплетов) на основе декларативных инструкций (схем/семантических контрактов).

## 1. Архитектурные требования к конвейеру данных (Pipeline)

Движок должен реализовывать преобразование данных по следующей схеме:
[Входные context-unbound данные] -> [Движок CCCR (Применение схем валидации и маппинга)] -> [Граф RDF / RDF-сериализация].

* Входные абстракции: Движок должен уметь парсить вложенные иерархические структуры типа <table label="..."> <row> <cell> .... Исходные ключи (например, "№ пп", "Уровень") признаются контекстно-зависимыми локальными идентификаторами.
* CSV: парсинг через glaze; табличные входы проецируются во внутреннее XML-представление `<registry>/<row id="…">/<cell label="…">` (заголовок CSV → `label`, строка → `row`), после чего к ним применяются те же XQuery-выражения, что и к XML/HTML.
* Выходные абстракции: Генерация классических триплетов «Субъект — Предикат — Объект». Поддерживаемые форматы вывода: RDF/XML (базовый), а также JSON/XML/HTML сериализация комплексных ответов SPARQL-запросов.


## 2. Ключевые компоненты и функционал ядра CCCR

### А. Генератор глобальных идентификаторов (URI/IRI Mapping)

* Движок обязан разрешать проблему локальных ID (например, превращать локальный идентификатор строки таблицы "1" в глобально уникальный URI).
* Правило формирования URI субъекта: `[Базовое пространство имен набора (Namespace)] + [#] + [Уникальный составной ключ сущности] (Пример: https://example.com)`.

### Б. Онтологический маппинг и типизация (Ontology Alignment)

* Инъекция типов (rdf:type): Каждому импортируемому объекту движок должен явным образом присваивать класс из целевой онтологии (например, https://example.com).
* Связывание предикатов: Локальные строковые имена признаков преобразуются в глобальные URI свойств в выделенном пространстве имен свойств (например, label="Год введения" $\to$ ex:годВведения в https://example.com).
* Интеграция внешних словарей: Поддержка предикатов эквивалентности (owl:sameAs) для связывания локальных свойств со стандартными внешними онтологиями (например, со спецификациями schema.org).

### В. Модуль объектных связей (Object Properties Resolver)

* Движок должен поддерживать трансформацию литеральных значений (Literal) в ссылки на ресурсы (Resource/URI). Строковые константы (например, "НО") при наличии инструкций в схеме CCCR должны преобразовываться в URI объектов resource=".../уровниОбразования#НО" для построения связанных графов .""", node=136)/>>.

### Г. Валидатор данных (Data Validation & Constraints)

Инструкции CCCR должны содержать правила для синтаксической и логической валидации значений признаков. Движок должен обрабатывать метаописания ограничений по аналогии с RDF Schema / SHACL:

* Проверка типов данных (rdfs:range, например xsd:positiveInteger).
* Диапазонные ограничения (интервалы значений, например xs:minInclusive = 2010).

### Д. Слой исполнения запросов (SPARQL Endpoint / Query Layer)

Сформированный движком семантический граф должен быть доступен для выполнения декларативных графовых запросов на языке SPARQL. Архитектура должна обеспечивать поиск сущностей по их типам, свойствам и метаописаниям свойств в условиях отсутствия жесткой априорной схемы данных (context-unbound querying).
