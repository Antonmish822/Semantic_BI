# CRM Pulse Monitor

Локальный read-only дашборд для текущего состояния CRM Bitrix24 в GraphDB или Fuseki. Реализован по мотивам [`rdf_store_monitor`](../rdf_store_monitor/README.md): сервер на стандартной библиотеке Python выполняет SPARQL `SELECT`, а браузер получает только готовый JSON.

## Что показывает

- всего активных сделок с `b24:stageSemantic "P"`;
- активные сделки, созданные за последние 24 часа, 7 и 30 дней;
- красные сделки: у сделок `P` нет записи активности, связанной с владельцем-сделкой (`OWNER_TYPE_ID=2`), за последние 7 дней;
- раскрывающийся список красных сделок с фильтром по категории, названием, ответственным, датой создания и `lastActivityTime` карточки Bitrix24;
- отдельный раскрывающийся список 20 последних активностей по сделкам: тема активности, семантический класс и название сделки, ответственный сотрудник;
- 20 сотрудников с наибольшим количеством назначенных сделок класса `b24:ActiveDeal`; список можно ограничить категорией проекта. При выбранной категории активности учитываются только записи, привязанные к сделкам этой категории (`OWNER_TYPE_ID=2`); в режиме «Все проекты» сохраняется общий подсчёт активностей по ответственному.

Окна времени вычисляются в SPARQL от `NOW()` GraphDB/Fuseki. Список сотрудников использует выведенный OWL-тип `b24:ActiveDeal` из `http://www.ontotext.com/implicit`; сводные KPI и список красных сделок используют исходный `b24:stageSemantic "P"`. Для активности используется поле `CREATED` (`b24:createdAt`), для даты сделки — `DATE_CREATE`. Активности в таблице сотрудников считаются по `responsible` для всех владельцев CRM, а проверка бездействия сделок — только для активностей, где владелец является сделкой (`ownerTypeId=2`). Последнее важно: в модели есть активности лидов, которые нельзя трактовать как активности сделок.

## Запуск локально

```bash
cd Semantic_BI/crm_pulse_monitor
cp .env.example .env
```

Проверьте `RDF_URL`. При локальном GraphDB используйте `http://127.0.0.1:7200`; при запуске внутри общей Docker-сети можно указать `http://graphdb:7200`. По умолчанию используется repository `fuseki_migration_monitor`. Если требуется, заполните `RDF_USERNAME` и `RDF_PASSWORD` в локальном `.env`; секреты в браузер не передаются.

```bash
python server.py
```

Откройте <http://127.0.0.1:8082>. Сервер по умолчанию привязан только к loopback. Данные обновляются автоматически раз в минуту; ответы API кэшируются на 30 секунд. Список красных сделок загружается только при раскрытии.

Для Fuseki задайте `RDF_BACKEND=fuseki` и `RDF_URL=http://127.0.0.1:3030/Persistent`.

## Структура

- `server.py` — HTTP API, конфигурация хранилища, read-only SPARQL client;
- `queries/` — отдельные запросы для KPI, сотрудников, категорий проектов, красного списка и последних активностей. Фильтр категории доступен отдельно для списка сотрудников и списка красных сделок.
- `static/` — интерфейс приложения.

Dashboard не пишет в RDF-хранилище. Метрики зависят от актуальности loader и доступности activity-событий в RDF.
