# План синхронизации Bitrix24 S3 → Fuseki

## Цель

Поддерживать в Fuseki актуальную RDF-проекцию событий экспортёра
`bitrix24_s3_export`. Каждая сущность Bitrix24 должна иметь стабильный
именованный граф. Новое событие обновляет этот граф, повторная доставка не
дублирует данные, а подтверждённое удаление удаляет граф.

## Решения по идентичности графа

Экспортёр создаёт новый файл и новый `event_id` для версии изменённой записи.
Поэтому ни имя файла, ни `event_id`, ни S3 `ETag` не подходят для постоянной
идентичности графа. Использовать `entity_key` из события, который уже включает
портал, тип сущности и ID записи.

```text
urn:bitrix24:entity:<portal>:<type>:<sha256(entity_key)>
```

Пример:

```text
urn:bitrix24:entity:garpix-bitrix24-ru:deal:<sha256>
```

`portal` и `type` кодировать как безопасные сегменты URI. Хешировать полную
строку `entity_key` в UTF-8. Так один и тот же объект из разных порталов
получает разные URI, а его версии из разных S3-файлов — одинаковый URI.

## Этапы изменений

### 1. Зафиксировать и проверить контракт S3

- Читать `state.json`, `runs/<run_id>/manifest.json` и, для облачных запусков,
  соответствующий `status.json`.
- Сначала применять принятый полный снимок, затем завершённые инкрементальные
  манифесты по порядку `window.to`/`created_at`.
- Не принимать событие только потому, что оно обнаружено листингом `events/`:
  ждать публикации завершённого манифеста.
- Для каждого объекта проверить SHA-256 байтов, `schema_version`, `event_id`,
  `graph_id`, `entity_key` и соответствие ключа S3 записи манифеста.
- Не применять `backfill` как обычный инкремент без явного режима.

### 2. Разделить синхронизатор на компоненты

- **S3 source:** чтение и валидация запусков и событий.
- **Mapper:** преобразование `event.payload` через схемы CCCR.
- **Fuseki client:** `PUT` и `DELETE` именованных графов через Graph Store API.
- **Checkpoint:** отдельный локальный SQLite-файл с постоянным путём и
  резервным копированием. Не использовать состояние экспортёра как checkpoint
  S3→Fuseki-синхронизатора.

Схемы CCCR и их registry должны иметь один определённый источник истины.
Предпочтительно хранить их в `Semantic_BI` и указывать локальный путь в
конфигурации; текущий синхронизатор ожидает получать registry и схемы из S3,
которых контракт экспортёра не обещает публиковать.

### 3. Применять версии в стабильный граф

Для события:

1. Разобрать `entity_key` и проверить, что портал совпадает с настроенным.
2. Вычислить URI графа по правилу выше.
3. Построить RDF из payload и отправить его через Graph Store `PUT` в этот URI.
   `PUT` заменяет содержимое графа целиком, включая факты, отсутствующие в
   новой версии.
4. После успешного ответа Fuseki записать `event_id`, `source_modified_at`,
   URI графа и применённую версию схемы в checkpoint.
5. Считать повтор уже применённого `event_id` успешной идемпотентной операцией.

Checkpoint должен также хранить завершённые `run_id`. Отмечать запуск
обработанным только после успешного применения всех его событий. Если процесс
завершился после `PUT`, но до записи checkpoint, повторный `PUT` безопасен.

При перекрытии окон и повторной доставке не позволять старой версии откатить
новую. Использовать порядок завершённых инкрементальных манифестов и
`source_modified_at`; `backfill` не должен перезаписывать текущую версию без
явного решения оператора.

### 4. Определить точные правила удаления

- **Старая версия события удалена из S3, новая версия того же `entity_key`
  осталась:** граф не удалять. Он уже содержит актуальную версию.
- **Подтверждённый tombstone от экспортёра:** удалить граф соответствующего
  `entity_key` через Graph Store `DELETE`, затем зафиксировать удаление в
  checkpoint.
- **Новый полный снимок:** сравнивать множество сущностей с checkpoint и
  удалять отсутствующие графы только для сущностей, для которых снимок
  действительно полный и авторитетный.
- **Активности:** отсутствие в снимке нельзя считать удалением, потому что
  экспортёр ограничивает снимок недавним окном.
- **Физическое удаление отдельного S3-файла:** само по себе не означает
  удаление CRM-сущности, если другой манифест содержит актуальное событие для
  того же `entity_key`.

Экспортёр сейчас не публикует удаления из Bitrix24. Для гарантированного
удаления таких сущностей потребуется добавить tombstone-события или согласовать
отдельную периодическую сверку полного набора записей.

### 5. Обновить конфигурацию и эксплуатацию

- Настроить точный портал и S3-префикс; не использовать пустой prefix.
- Хранить SQLite checkpoint между перезапусками.
- Использовать постоянное Fuseki-хранилище: текущий Compose запускает
  in-memory dataset.
- Добавить понятные логи для пропуска, повтора, обновления и удаления графа;
  не писать содержимое событий и секреты в лог.
- При миграции с URI `urn:cccr:s3:...` загрузить и сверить актуальное состояние,
  затем удалить старые графы ограниченным запросом/списком. Не удалять старые
  графы до успешного импорта новой схемы.

## Критерии готовности

- Два разных S3-файла с версиями одной сделки обновляют один и тот же URI.
- После обновления в графе нет устаревших троек от предыдущей версии.
- Повтор одного манифеста не создаёт дубликатов и не откатывает версию.
- Незавершённый запуск и событие с неверной контрольной суммой не меняют
  Fuseki и не двигают checkpoint.
- Удаление старого файла версии не удаляет граф, если актуальная версия
  сущности существует.
- Подтверждённый tombstone удаляет ровно один граф; повтор удаления безопасен.
- Перезапуск синхронизатора продолжает с checkpoint, а полный snapshot применяет
  согласованную политику сверки с учётом неполного окна активностей.

## Статус реализации

В ветке `feat/entity-key-fuseki-sync` реализованы основные пункты плана:

- Синхронизатор читает принятый snapshot и завершённые incremental manifests,
  сверяет SHA-256 событий и статус запуска.
- Все версии `entity_key` направляются в URI
  `urn:bitrix24:entity:<portal>:<type>:<sha256(entity_key)>`.
- Обработанные сущности и запуски фиксируются в SQLite; повторный `PUT`
  безопасен при перезапуске после сбоя.
- Fingerprint registry и схем CCCR входит в checkpoint; при изменении mapping
  текущие сущности повторно проецируются из сохранённых событий S3.
- Схемы CCCR читаются из локального registry `Semantic_BI`.
- Snapshot reconciliation удаляет пропавшие сущности для настроенного списка
  полных типов; активности в этот список по умолчанию не входят.
- Обновлены конфигурация и документация запуска.

Остаются ограничения источника и эксплуатации:

- Экспортёр пока не публикует tombstone при удалении записи в Bitrix24.
- Если consumer отстал за предел срока хранения run-манифестов, он останавливает
  инкрементальную обработку и требует нового полного снимка.
- Для сохранности между перезапусками нужно хранить SQLite checkpoint и
  использовать persistent Fuseki dataset.
- Перед миграцией нужно отдельно удалить старые `urn:cccr:s3:*` графы после
  успешной сверки нового импорта.
