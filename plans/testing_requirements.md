# Требования к тестированию Semantic_BI S3 → Fuseki

## Цель

Подтвердить, что загрузчик применяет только завершённые и проверенные события
экспортёра Bitrix24, строит RDF через CCCR и поддерживает в Fuseki ровно одну
актуальную версию графа для каждой CRM-сущности.

Тесты должны работать без реальных S3, Bitrix24 и Fuseki. Внешние границы
подменяются управляемыми фикстурами и mock/stub-клиентами. Отдельный небольшой
интеграционный прогон допускается с локальным Fuseki и установленным `cccr_py`.

## Обязательные уровни

### 1. Модульные тесты

- `entity_graph_uri`: один `entity_key` всегда даёт один URI; разные portal,
  тип сущности или identity дают разные URI; хеш вычисляется от полной UTF-8
  строки `entity_key`.
- JSON → XML: проверить строковые значения, числа, boolean, `null`, вложенные
  объекты и массивы; XML должен быть корректным, а отсутствие/не-объектный
  `payload` должно давать понятную ошибку.
- Mappings и CCCR: выбор схем по относительному S3-ключу, отсутствие mapping,
  некорректная схема, ошибка выполнения CCCR, объединение нескольких графов и
  сериализация результата в RDF/XML.
- Контракт события: проверить `schema_version`, `event_id`, `graph_id`,
  `entity_key`, портал, тип/ID сущности, операцию и согласованность S3 key с
  манифестом. Некорректные значения не должны достигать Fuseki.
- Контрольная сумма: совпадающий SHA-256 принимается, несовпадающий приводит к
  отказу до трансформации и записи в Fuseki.
- Порядок событий: повтор версии идемпотентен; более старая версия не должна
  перезаписывать новую; событие без допустимого времени обрабатывается согласно
  явно заданным правилам и не вызывает случайный откат.
- Конфигурация и registry: проверять обязательные параметры, безопасное
  разрешение путей схем внутри `schemas_root`, regex/match mode и fingerprint
  реестра/схем.

### 2. Тесты применения к Fuseki

Использовать fake HTTP transport и проверять HTTP-метод, dataset endpoint,
query-параметр `graph`, заголовок `Content-Type`, тело и допустимые статус-коды.

- `upsert` отправляет RDF/XML через Graph Store `PUT` на стабильный URI графа.
- Две версии одного `entity_key` направляются в один URI; вторая операция —
  полный `PUT`, а не добавление (`POST`) троек.
- `delete` отправляет `DELETE` на тот же URI и отмечает сущность удалённой в
  checkpoint; повторное удаление безопасно.
- Ошибка HTTP/таймаут не фиксирует событие или run как успешно применённые.
- Проверить авторизацию при заданных учётных данных и отсутствие auth при
  пустом username.

### 3. Тесты манифестов, снимка и checkpoint

- Незавершённый manifest или incremental run без `status.json: complete` не
  меняет Fuseki и checkpoint. Завершённые manifest и status обрабатываются.
- Объекты берутся из `objects[]`, а не из произвольного листинга `events/`;
  проверяются ключ, event ID, SHA-256 и допустимый режим запуска.
- Ошибка на середине run: run не отмечается завершённым; после рестарта успешно
  применённые сущности можно безопасно пропустить, остальные применяются.
- Сбой после успешного `PUT`, но до checkpoint: повторный запуск безопасно
  выполняет тот же `PUT` и восстанавливает checkpoint.
- Сбой записи checkpoint не должен ошибочно отмечать run завершённым.
- Новый авторитетный snapshot применяет события, а затем удаляет только
  отсутствующие типы, перечисленные в `snapshot_reconcile_entity_types`.
  Активности вне этого набора не удаляются из-за неполного временного окна.
- Повторный snapshot/run не меняет итоговое содержимое и состояние.
- При изменении fingerprint mapping/schema текущие сущности повторно
  проецируются; после успеха checkpoint содержит новую версию fingerprint.
- Одновременный второй процесс с тем же checkpoint корректно блокируется.
- Отсутствие требуемой истории run manifests приводит к явной ошибке/требованию
  нового snapshot, а не к молчаливому пропуску окна.

### 4. Контрактные и интеграционные тесты

- Фикстуры событий и манифестов должны соответствовать реальному контракту
  `bitrix24_s3_export`; при изменении контракта проверка должна явно падать.
- Для каждого поддерживаемого типа сущности проверить путь ключа, mapping и
  ожидаемые RDF-тройки на небольшом репрезентативном payload.
- С установленным CCCR преобразовать payload в RDF/XML и разобрать сериализацию
  RDF независимым парсером либо загрузить её в локальный Fuseki.
- На локальном Fuseki подтвердить семантику замены: загрузить версию A, затем
  версию B, проверить, что тройки, присутствовавшие только в A, отсутствуют.
- Проверить удаление named graph и разделение графов между порталами и типами.

## Фикстуры

Минимальный набор: завершённый полный snapshot; два последовательных события
одной сущности; два портала; события разных типов; tombstone/delete для
потребительского контракта; событие с неверным SHA-256; повреждённый JSON;
невалидная identity; незавершённый manifest/status; частично применённый run;
пустой и изменённый payload; mapping с одной и несколькими схемами.

Секреты, production-данные и сетевые обращения к корпоративной инфраструктуре
в тестах не используются.

## Критерии готовности

1. Все модульные, Fuseki-контрактные и snapshot/checkpoint-тесты проходят в CI.
2. Каждая операция `upsert` доказывает замену полного графа по стабильной
   идентичности; тест проверяет отсутствие устаревших троек.
3. Ошибочные/незавершённые источники не меняют Fuseki и не передвигают
   checkpoint.
4. Повтор после сбоя и повторная доставка дают тот же конечный RDF и состояние.
5. Интеграционный тест CCCR/Fuseki проходит в отдельной среде; его пропуск в
   обычном локальном окружении обозначается явно, а не считается успехом.
6. Удаление CRM-сущностей считается гарантированным только если экспортёр
   публикует tombstone либо загрузчик выполняет авторитетную полную сверку.

## Текущее состояние

На момент составления документа прикладных тестов загрузчика в репозитории нет;
`python -m unittest discover` обнаруживает 0 тестов. `py_compile` проверяет
только синтаксис. Тесты, поставляемые внутри каталога `cccr_engine`, относятся
к движку CCCR и не покрывают S3 → Fuseki интеграцию.
