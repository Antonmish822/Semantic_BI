# План упрощения архитектуры Semantic_BI

## Целевая архитектура

`Semantic_BI` содержит конкретный сценарий **Bitrix24 S3 → RDF-хранилище** с адаптерами Fuseki и GraphDB. `cccr_engine` подключён напрямую как закреплённый Git submodule и отвечает за преобразование данных по схемам CCCR. Репозиторий `cccr_pipeline` перестаёт быть зависимостью `Semantic_BI`: код действующего синхронизатора переносится в основной репозиторий.

```text
Semantic_BI/
├── README.md                    # действующая схема системы и запуск
├── RDF_INTEGRATION.md           # контракт с экспортёром Bitrix24
├── .gitmodules                  # прямое подключение cccr_engine
├── cccr_engine/                 # библиотека преобразования в RDF
├── mappings/bitrix24/
│   ├── registry.json            # единый реестр схем
│   └── schemas/*.json           # схемы CCCR
├── pipelines/
│   ├── core/
│   │   ├── graph_store.py       # контракт операций с именованными графами
│   │   ├── checkpoint.py        # SQLite-состояние и возобновление
│   │   └── runner.py            # порядок применения операций
│   ├── stores/
│   │   ├── fuseki.py            # адаптер Fuseki
│   │   └── graphdb.py           # адаптер GraphDB
│   └── bitrix24/
│       ├── cli.py               # точка входа и выбор RDF-хранилища
│       ├── config.py            # загрузка и проверка настроек
│       ├── source.py            # контракт манифестов и событий Bitrix24 в S3
│       ├── mapper.py            # подготовка payload и вызов cccr_engine
│       ├── identity.py          # URI графа по entity_key
│       └── reconciliation.py    # политика снимков и удаления
├── tests/
│   ├── test_loader.py           # контракт, pipeline и оба store adapter
│   └── bitrix24/fixtures/        # обезличенные RDF payload fixtures
├── deploy/loader/
│   ├── Dockerfile
│   ├── compose.yaml
│   └── config.example.yaml
├── raw_ingest/                  # отдельный коннектор; его статус описан явно
└── rdf_store_monitor/           # интерфейс чтения RDF-хранилища
```

Конфигурация сценария задаёт пути к схемам, S3, выбранное RDF-хранилище и checkpoint. Секреты не хранятся в Git; файл SQLite остаётся в постоянном томе. В `README.md` следует отдельно показывать действующий поток данных и целевую архитектуру платформы, чтобы планы развития не выглядели уже реализованными.

### Контракт RDF-хранилища

Общий `runner` вызывает операции `replace_graph(graph_uri, rdf_bytes)` и `delete_graph(graph_uri)` через интерфейс `graph_store`. Оба адаптера должны обеспечивать полную замену одного именованного графа и безопасный повтор операции; checkpoint обновляется только после успешного ответа хранилища. URI графа и решение об удалении определяются сценарием Bitrix24, а не адаптером.

Адаптер Fuseki использует Graph Store endpoint существующего загрузчика. Адаптер GraphDB использует Graph Store HTTP Protocol репозитория: `PUT` заменяет содержимое именованного графа, `DELETE` удаляет его. Адрес репозитория, авторизация и параметры соединения задаются отдельно для каждого адаптера. Перед переключением хранилища требуется начальная загрузка и сверка графов: смена адаптера не переносит RDF-данные и не должна автоматически переиспользовать checkpoint прежнего хранилища.

`pipelines/core` остаётся внутренней частью проекта до появления второго реального сценария. Его можно будет выделить в библиотеку, если новый сценарий реализуется без правок общего кода.

## План рефакторинга и миграции

1. **Зафиксировать текущий контракт — выполнено.** Записаны URI графов, формат checkpoint, правила удаления и результаты проверок.
2. **Убрать дублирование данных — выполнено.** Схемы и единый registry находятся в `mappings/bitrix24`; Docker использует их из основного репозитория.
3. **Перенести код сценария — выполнено.** Runtime-код находится в `pipelines/`, операции именованных графов вынесены в общий интерфейс.
4. **Подключить движок напрямую — выполнено локально.** `cccr_engine` подключён корневым submodule; зависимости, lock-файл и workflow обновлены. Зависимость runtime от `cccr_pipeline` удалена.
5. **Добавить адаптер GraphDB — выполнено.** Оба адаптера покрывают общий Graph Store контракт; контрактные тесты и отдельный GraphDB прогон выполнены.
6. **Перенести развёртывание — выполнено.** Compose и пример конфигурации находятся в `deploy/loader/`; workflow публикует loader и monitor образы в GHCR только после push Git-тега `v*`, а Compose требует явно выбрать release или SHA tag. Сборка на сервере не выполняется.
7. **Проверить миграцию — выполнено для текущего сценария.** Fuseki full-checkpoint rehearsal и GraphDB тестовый прогон завершены. GHCR образы скачаны и запущены; монитор ответил HTTP 200, Fuseki доступен, loader был догнан до последнего exporter run. Полная GraphDB checkpoint-репетиция пропущена по решению пользователя.

Переключать рабочий сервис следует после проверки совместимости checkpoint. Если его формат придётся изменить, нужен отдельный версионированный скрипт миграции и резервные копии SQLite и соответствующего RDF dataset/repository.
