# План перехода загрузчика S3 → RDF на контракт 2

> Исторический план реализации. Runtime загрузчика работает только на контракте 2;
> инструкции по текущей эксплуатации см. в [runbook](../LOADER_CONTRACT_V2_RUNBOOK.md).

Статус: проект плана для реализации и приёмки. Нормативный протокол — [S3_SYNC_CONTRACT_PROPOSAL.md](../../../S3_SYNC_CONTRACT_PROPOSAL.md). Реализованный экспортёр находится в `../bitrix24_s3_export/v2/`; его контрольные векторы — в `../bitrix24_s3_export/docs/contract_v2_test_vectors.json`, порядок переключения — в `../bitrix24_s3_export/docs/CONTRACT_V2_CUTOVER_RUNBOOK.md`. Абстрактные сценарии и их ограничения описаны в `../bitrix24_s3_export/docs/state_machine/`.

План касается загрузчика `Semantic_BI/pipelines/bitrix24`, его SQLite checkpoint, конфигурации, мониторинга и резервного копирования. Цель — получить готовый потребитель контракта 2 для окончательной проверки полного цикла экспортёр → S3 → RDF. Действующий путь контракта 1 остаётся доступным до контролируемого перехода; два пути не обрабатывают один портал и RDF-хранилище одновременно.

## Исходное состояние и решение по архитектуре

Сейчас `source.py` читает старый `state.json`, проверяет старую формулу `event_id`; `runner.py` находит запуски через листинг `runs/`, сравнивает ID и требует `status.json`. Checkpoint версии 1 хранит `base_manifest_key` и `last_run_id`, но не epoch, SHA вершины и ревизию указателя. У экспортёра v2 подтверждённые запуски образуют цепочку `previous_run_id`/`previous_manifest_sha256` от `tip_run_id` в `state.json`; `status.json` является только диагностикой.

Создать в `pipelines/bitrix24/v2/` отдельные модули для разбора контракта, проверки объектов и обхода цепочки. Повторно использовать `mapper.py`, `identity.py`, `GraphStore`, `apply_graph_operation` и механизмы блокировки SQLite. Диспетчер в `cli.py` выбирает путь **по проверенному `state.json.contract_version`** и закрепляет выбранную эпоху/версию за checkpoint. Не импортировать runtime-код экспортёра в загрузчик: две стороны независимо реализуют контракт и сверяются общими контрольными векторами.

## Этап 0. Зафиксировать совместимость и контрольные данные

**Работы**

1. Сверить [контракт](../../../S3_SYNC_CONTRACT_PROPOSAL.md) с фактическим форматом экспортёра `../bitrix24_s3_export/v2/format.py`, `state.py`, `orchestrator.py`, `snapshot.py`; записать точный состав обязательных и допустимых полей. Обнаруженные расхождения разрешить до написания валидатора, не угадывая намерение экспортёра.
2. Скопировать в независимые тестовые fixtures загрузчика контрольные векторы контракта 2. Включить кириллицу, дробные числа, UTC со смещением и микросекундами, `null`, составной ID `stage/source`, связи активности и пустой incremental.
3. Подготовить синтетический набор: полный снимок, два последовательных incremental запуска, повторное событие, пустой запуск, отдельный backfill, новая эпоха и повреждённый объект. Хранить только вымышленные CRM-данные.
4. Зафиксировать ожидаемый результат RDF по `entity_key` и список графов после каждого этапа, включая сверку отсутствующих сущностей.

**Критерии приёмки**

- Независимый код загрузчика воспроизводит `event_id`, канонические байты и SHA всех контрольных векторов.
- Для каждого синтетического манифеста известны ожидаемые checkpoint и набор RDF-графов; реальные CRM-данные и секреты в fixtures не входят.
- Все расхождения текста контракта с фактическим экспортёром документированы и разрешены до этапа 1.

## Этап 1. Реализовать безопасное чтение и проверку контракта 2

**Работы**

1. Добавить валидатор `state.json`: `contract_version = 2`, `revision`, `epoch_id`, ключ/SHA базового снимка и парные `tip_run_id`/`tip_manifest_sha256`. Проверять портал и допустимые префиксы всех ключей. Один раз прочитанный `state.json` становится неизменной верхней границей текущего цикла.
2. Добавить валидаторы snapshot и incremental/backfill манифестов: `run_id`, `epoch_id`, `mode`, `status`, `complete`, `complete_entity_types`, `window`, парные ссылки на предшественника, уникальность ключей и точные `counts` всех шести типов, включая нули.
3. Для каждого манифеста проверять SHA **сырых скачанных байтов** против SHA из указателя или следующего звена цепочки; затем проверять структуру и соответствие каноническому JSON. SHA metadata S3 проверять дополнительно, но не использовать вместо SHA тела.
4. Для каждого события сверять SHA скачанного тела с `objects[].sha256`, затем JSON, ключ, portal, entity, `entity_key`, `graph_id`, `event_id_algorithm = 3` и самостоятельно рассчитанный `event_id`. Для старого формата оставить отдельный валидатор и старые правила.
5. Ошибки проверки не должны логировать CRM payload, секреты или тело объекта. Диагностика содержит безопасные ключ, run ID, ожидаемый/фактический SHA и класс ошибки.

**Критерии приёмки**

- Корректные контрольные векторы принимаются; замена одного байта в событии или манифесте отклоняется до RDF-записи.
- Неверная эпоха, чужой портал, повтор ключа, неверные counts, неподдерживаемый алгоритм ID и неканоническое тело отклоняются.
- Старые fixtures продолжают читаться прежним путём; v2-объект не принимается по правилам v1.

## Этап 2. Реализовать обход подтверждённой цепочки

**Работы**

1. Строить очередь **от `state.json.tip_run_id` назад** по `previous_run_id` и `previous_manifest_sha256`, проверяя SHA каждого манифеста, принадлежность одной эпохе, отсутствие цикла, соответствие ключа `run_id`, допустимое окно и неубывание `window.to`. Затем применять необработанные звенья в прямом порядке.
2. Остановить обратный обход только на точном совпадении `(epoch_id, run_id, manifest_sha256)` с checkpoint либо на `previous_run_id = null`. Если checkpoint указывает на run, которого нет в подтверждённой цепочке, прекращать цикл с диагностикой; не начинать с произвольного найденного манифеста.
3. Для v2 не использовать листинг `runs/`, лексикографическую сортировку `run_id` и `status.json` как критерий подтверждения. Backfill не входит в регулярную цепочку и не применяется автоматически.
4. Если tip пустой, после принятого snapshot корректно завершать цикл. Если между двумя циклами указатель вырос, новый tip обрабатывается в следующем цикле.

**Критерии приёмки**

- Два и более запуска применяются ровно в порядке ссылок, включая пустой запуск; неподтверждённый manifest и `status.json: failed` вне цепочки не блокируют обработку.
- Разрыв, цикл, неверный SHA предшественника, потеря объекта по retention и checkpoint вне цепочки останавливают цикл без продвижения позиции.
- Смена tip во время цикла не меняет сохранённую верхнюю границу этого цикла.

## Этап 3. Перевести checkpoint на версию 2

**Работы**

1. Добавить к checkpoint поля `contract_version`, `epoch_id`, `base_manifest_key`, `base_manifest_sha256`, `applied_tip_run_id`, `applied_tip_manifest_sha256`, `observed_state_revision` и версию mappings; при необходимости расширить таблицу `runs` SHA манифеста и epoch.
2. Разделить две операции: checkpoint отдельной сущности после подтверждённого Graph Store PUT/DELETE и отметку завершённого run после успешного применения **всех** ссылок. Повтор записи того же run с иным SHA считать конфликтом, а не скрывать через `INSERT OR IGNORE`.
3. Определить безопасный переход v1 → v2: остановить старый загрузчик, сделать согласованную резервную копию RDF и SQLite, проверить привязку checkpoint к конкретному backend/dataset, затем применить новый полный снимок v2. Не переписывать старый `last_run_id` в вершину новой цепочки.
4. После прерывания на середине snapshot возобновлять по сохранённым сущностям; `base_manifest_sha256` фиксировать только после всех событий и допустимой сверки. После смены эпохи сбрасывать только позицию incremental-цепочки; сведения о применённых сущностях сохранять для сверки и безопасного повтора.
5. Обновить блокировку checkpoint и схему резервного копирования/восстановления: пара RDF + SQLite должна соответствовать одной эпохе и одной подтверждённой вершине.

**Критерии приёмки**

- Сбой между RDF PUT/DELETE и SQLite записью приводит к безопасному повтору; run не отмечен завершённым преждевременно.
- Сбой в середине snapshot возобновляется без ложного завершения базы или удаления сущностей.
- Восстановленный checkpoint с другой эпохой, RDF endpoint или SHA run блокируется до явного перехода/восстановления.
- Резервная копия и status-файл отражают epoch, SHA базы и SHA вершины; проверка backup barrier остаётся работоспособной.

## Этап 4. Применить snapshot и сверку сущностей

**Работы**

1. При новой `epoch_id` проверить базовый ключ и SHA из `state.json`, загрузить все события snapshot и применить их в стабильные именованные RDF-графы по `entity_key`.
2. Сверять отсутствующие сущности только для пересечения `manifest.complete_entity_types` и настроенного локального разрешения `snapshot_reconcile_entity_types`. Если тип не объявлен полным, его старые графы не удалять. `activity` при оконном снимке никогда не сверять по отсутствию.
3. Выполнять удаление отсутствующих графов только после полного чтения и проверки snapshot. Сбой при сверке оставляет базу незавершённой и возобновляется идемпотентно.
4. Затем строить и применять incremental цепочку новой эпохи, включая окно, которое перекрывает `t0`; уже применённые версии не должны создавать повторный эффект. Не пропускать целый run только по сравнению его `window.to` с `catchup_to`.

**Критерии приёмки**

- Полный снимок с допустимыми типами даёт ожидаемый набор графов; отсутствие `activity` и любого не объявленного полным типа не удаляет графы.
- Повреждение последнего события snapshot блокирует завершение базы и сверку отсутствующих сущностей.
- Смена эпохи и последующий догон дают тот же конечный RDF-набор при обычной работе и после повторного запуска с каждой точки сбоя.

## Этап 5. Обработать повтор, fast-режим и изменение mappings

**Работы**

1. В строгом режиме сверять тело каждого события при повторном проходе. В `fast`-режиме разрешать пропуск только точного совпадения `key`, SHA ссылки, `event_id`, URI графа, версии mappings и сохранённого checkpoint.
2. Явно обозначить предел `fast`: последующая порча пропущенного в S3 объекта не обнаруживается в этом проходе. Для окончательной проверки полного цикла использовать строгий режим и отдельный полный аудит доступных ссылок.
3. При изменении fingerprints mappings перепроецировать активные графы из сохранённых S3 event keys с проверкой SHA. Недоступный исходный объект обрабатывать по явной политике: остановка для полных типов; отдельная диагностика для старых оконных activity, без молчаливого утверждения об успешной перепроекции.
4. Проверить `delete` на уровне Graph Store и checkpoint как идемпотентную операцию старого формата; v2 экспортёр пока публикует `upsert`, поэтому отсутствие tombstone не трактовать как удаление вне разрешённой snapshot-сверки.

**Критерии приёмки**

- Повтор при неизменных данных не меняет конечный граф; `fast` не пропускает изменённый SHA или mapping fingerprint.
- Строгий режим обнаруживает повреждение уже обработанного события при его следующем фактическом чтении; предел `fast` показан отдельным проверяемым сценарием.
- Перепроекция с отсутствующим обязательным источником не отмечается завершённой.

## Этап 6. Интегрировать выбор протокола и эксплуатационные средства

**Работы**

1. В `cli.py` определить путь v1/v2 по `state.json.contract_version` и привязке checkpoint. Не разрешать автоматическое понижение v2 checkpoint до v1 при временном чтении старого/повреждённого указателя.
2. В конфигурации оставить существующие S3, backend, mappings и путь checkpoint; добавить только необходимые настройки версии/режима проверки и верхние ограничения на длину цепочки, число объектов и время чтения. Отсутствие ответа или слишком длинная цепочка — явная ошибка, а не пропуск.
3. Обновить `status.json` загрузчика: версия контракта, epoch, SHA базы, применённый run/SHA, наблюдаемая ревизия `state.json`, состояние `waiting/blocked/error`. Не включать CRM payload или S3 credentials.
4. Обновить backup/restore, мониторинг и документацию `RDF_INTEGRATION.md`, `S3_TO_FUSEKI_LOADING.md`, `SYNC_RUNBOOK.md`, описание конфигурации и образ контейнера. Сохранить совместимость с Fuseki и GraphDB.

**Критерии приёмки**

- v1 продолжает работать с v1-указателем, v2 — с v2; неверная или регрессировавшая версия указателя не меняет RDF и checkpoint.
- Оба backend и `--once`/непрерывный режим проходят одинаковые сценарии целостности и возобновления.
- Backup barrier делает согласованную копию RDF/checkpoint; мониторинг показывает реальное отставание от tip и причину блокировки.

## Этап 7. Окончательная проверка полного цикла

**Работы**

1. На изолированном bucket и RDF dataset/repository опубликовать v2 snapshot и несколько incremental запусков реальным кодом экспортёра, включая пустой run, повтор, справочники и смену snapshot. Импортировать тем же кодом, который будет выпущен.
2. Сверить все контрольные векторы независимо от экспортёра. Сравнить число ссылок, checksum и ожидаемые RDF-графы по каждому типу и итоговый checkpoint. Не считать одни лишь успешные exit codes подтверждением содержимого.
3. Внедрить сбой после каждого шага импортёра: чтение указателя, обход цепочки, скачивание события, RDF PUT/DELETE, запись checkpoint сущности, завершение run и snapshot-сверка. После возобновления сравнить конечное состояние с запуском без сбоя.
4. Воспроизвести инцидент категории `112`: подменённые байты под ключом, на который ссылается подтверждённый snapshot, должны остановить загрузчик до применения события; восстановление исходных байтов или новая эпоха возвращают поток к рабочему состоянию. Отдельно подтвердить, что старый `status.json` не влияет на v2-цепочку.
5. Проверить двух независимых импортёров с разными checkpoint и отставанием, а также backup/restore на копии данных. Для рабочего S3 использовать только read-only диагностику до согласованного переключения.

**Критерии приёмки**

- Экспортёр v2 → S3 → каждый backend RDF даёт ожидаемые графы и точное совпадение обработанного `(epoch_id, tip_run_id, tip_manifest_sha256)`.
- После каждой внедрённой ошибки повтор сходится к тому же результату без пропуска run и без принятия изменённых байтов.
- Инцидентный сценарий блокируется с безопасной диагностикой; `fast` не заявляется полной проверкой S3-истории.
- Отчёт фиксирует версии обоих компонентов, конфигурацию без секретов, результаты сравнения RDF/checkpoint и оставшиеся инфраструктурные ограничения.

## Этап 8. Подготовить выпуск и переход

**Работы**

1. Выпустить образ загрузчика, содержащий оба пути, но запускать его на рабочем RDF только после резервной копии пары RDF + SQLite и проверки указателя S3.
2. Согласовать порядок с runbook экспортёра: готовность загрузчиков → публикация нового snapshot/эпохи → контролируемый incremental → подтверждение вершины каждым активным загрузчиком → регулярный опрос.
3. Сохранить старый checkpoint и backup до подтверждения перехода; после публикации v2 не запускать старый загрузчик против v2 `state.json`. При ошибке остановить применение, сохранить диагностику и восстановить согласованную пару RDF/checkpoint либо исправить v2 и повторить; не подменять SHA в checkpoint.

**Критерии приёмки**

- Есть проверяемый порядок переключения, восстановления и критерий окончания перехода для каждого активного загрузчика.
- До рабочей публикации новый загрузчик прошёл этап 7; после неё `status.json` подтверждает новую эпоху и достижение вершины цепочки.
- Старые объекты и backup сохраняются в пределах согласованного срока, пока могут понадобиться отстающим клиентам.

## Зависимости и границы

Этапы 0–2 завершаются до изменения рабочего checkpoint. Этапы 3–5 зависят от валидатора v2 и могут проверяться на синтетическом S3. Этап 6 объединяет два пути и backup. Этап 7 требует готового экспортёра v2 и изолированных S3/RDF ресурсов; этап 8 выполняется только после его приёмки. Модели TLA+ проверяют абстрактные свойства протокола, но не заменяют проверку Python-кода и операций целевого S3.
