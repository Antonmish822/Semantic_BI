# Сквозная приёмка контракта 2: Bitrix24 → экспортёр → S3 → загрузчик → RDF

Статус: план, проверки по нему ещё не засвидетельствованы. Это этап 7
[плана загрузчика](LOADER_CONTRACT_V2_IMPLEMENTATION_PLAN.md) и этап 7
[плана экспортёра](../../bitrix24_s3_export/docs/EXPORTER_V2_IMPLEMENTATION_PLAN.md).
Следующий шаг после подписанного отчёта — контролируемое переключение по
[runbook экспортёра](../../bitrix24_s3_export/docs/CONTRACT_V2_CUTOVER_RUNBOOK.md)
и [runbook загрузчика](LOADER_CONTRACT_V2_RUNBOOK.md).
Нормативные поля и алгоритмы определяет
[контракт](../../S3_SYNC_CONTRACT_PROPOSAL.md).
Для выделенного тестового Yandex S3 соблюдать
[инструкцию доступа](../../bitrix24_s3_export/docs/AI_AGENT_YANDEX_S3_ACCESS.md)
и [инструкцию синтетической S3-приёмки](../../bitrix24_s3_export/docs/AI_AGENT_S3_E2E_ACCEPTANCE.md).
Конфиг `local-data/s3-v2-test/config.json` по инструкции доступа разрешён
только для синтетических проверок; не подключать к нему importer. Полный
прогон загрузчика требует отдельно предоставленного тестового S3-доступа
и изолированного RDF. Пока этого нет, соответствующие E2E/INT/REC сценарии
имеют статус `BLOCKED`, даже если S3-пробы прошли.

## 1. Цель и границы

Доказать на изолированных ресурсах, что **те же версии кода**, которые будут
выпущены, публикуют подтверждённую цепочку v2 и воспроизводят её в RDF без
пропусков, принятия изменённых байтов и потери прогресса после сбоев. Проверить
оба RDF backend, которые планируется эксплуатировать: Fuseki и/или GraphDB.
Если backend не испытывался, допуск к выпуску на нём не выдаётся.

Приёмка использует отдельные S3 bucket или portal prefix, YDB state/table,
RDF dataset/repository, учётные данные и SQLite checkpoint. Не писать в рабочий
S3 prefix, рабочую YDB state/table или рабочий RDF. Проверки порчи и конфликтов
проводятся только на специально созданных тестовых объектах. Реальные CRM
payload и секреты в отчёт не включать.

Локальный образ загрузчика для первого прогона:
`semantic-bi-loader:feat-loader-contract-v2`. Перед началом зафиксировать его
полный digest/ID, commit исходников, версию экспортёра и digest его артефакта.
Повторить критерии приёмки на итоговых release артефактах, если их digest
отличается от испытанных.

## 2. Входные условия и владельцы

| Условие | Проверка до первого запуска | Ответственный |
| --- | --- | --- |
| Изолированный S3 и YDB | Отдельные prefix, bucket policy, state/table, credentials; явная маркировка test | владелец инфраструктуры/экспортёра |
| Доступ для полного importer-прогона | Отдельное явное разрешение и тестовый S3-конфиг; закрытый `local-data/s3-v2-test/config.json` используется только в границах своей инструкции | владелец S3/загрузчика |
| Изолированный RDF | Новый dataset/repository на каждом проверяемом backend; endpoint identity и права PUT/DELETE | владелец RDF/загрузчика |
| Артефакты | Digest образа загрузчика, SHA пакета/образа экспортёра, commit и конфигурация без секретов | владельцы компонентов |
| Источник тестовых данных | Управляемый тестовый портал или воспроизводимый CRM fixture с сущностями, справочниками и изменениями между запусками | владелец CRM |
| Полнота snapshot | Подтверждённые scopes и успешная выгрузка всех страниц для каждого типа в `complete_entity_types`; `activity` не включать | владелец CRM/экспортёра |
| S3 семантика | На целевом *тестовом* endpoint проверить `If-None-Match`, `If-Match`, конкурентный Put, неизвестный ответ и bucket policy по [runbook](../../bitrix24_s3_export/docs/CONTRACT_V2_CUTOVER_RUNBOOK.md#тестовый-бакет) | владелец S3 |
| Повторяемость | Инструмент сброса только тестового namespace и тестовых RDF/SQLite; зафиксированные исходные данные и ожидаемые изменения | ведущий приёмки |
| Независимый оракул | Скрипт/процедура чтения опубликованных *сырых* объектов и RDF, не использующая runtime-модули экспортёра/загрузчика | ведущий приёмки |

При отсутствии ресурса или возможности внедрить конкретный сбой отметить
проверку `BLOCKED` с причиной. Не записывать `PASS` по результату unit-теста
вместо реального интеграционного прогона.

## 3. Подготовка стенда и исходной точки

1. Создать идентификатор прогона, например `acceptance-YYYYMMDD-NN`, и
   отдельный каталог доказательств. Зафиксировать UTC время, участников, версии
   кода, digest артефактов, S3 endpoint/region/bucket/portal prefix,
   YDB table identity, RDF backend/dataset, mapping fingerprint, конфигурацию
   лимитов и `resume_mode: strict`. Маскировать credentials и payload.
2. Развернуть тестовый экспортёр с v2 и тестовой YDB state/table. Ограничить
   writer credentials тестовым prefix. Проверить read-only, что рабочий
   `state.json` и рабочая YDB state/table не затронуты.
3. Подготовить на каждый RDF backend по крайней мере два независимых
   dataset/repository и два отдельных SQLite checkpoint. Первый нужен для
   обычного потока, второй — для отстающего потребителя. Не делить checkpoint
   между одновременно запущенными загрузчиками.
4. Создать конфигурацию загрузчика по
   [`deploy/loader/config.example.yaml`](../deploy/loader/config.example.yaml):
   тестовый S3, выбранный RDF endpoint, отдельный checkpoint,
   `checkpoint.resume_mode: strict`, разрешённые типы reconciliation и лимиты.
   Конфигурация и checkpoint должны находиться вне образа и вне Git.
5. Для проверки совпадения байтов и формата использовать опубликованные
   [`contract_v2_test_vectors.json`](../../bitrix24_s3_export/docs/contract_v2_test_vectors.json)
   и независимый расчёт canonical JSON/SHA-256. Записать ожидаемые URI графов,
   набор entity key и контрольные RDF утверждения для тестовых данных.
6. Перед каждым негативным сценарием сохранить копию **тестовых** S3 объектов,
   RDF и checkpoint либо запустить его в новом тестовом namespace. Удаление
   тестовых объектов выполнять только после сохранения доказательств.

### Пример однократного запуска подготовленного образа

Команда выполняется из `Semantic_BI`; здесь `./acceptance/loader-v2.yaml` —
локальная конфигурация тестового стенда, а `acceptance_loader_state` — новый
Docker volume. Подставить Docker network, в которой доступен RDF endpoint.
При bind mount конфигурации с правами `0600` запустить контейнер под UID/GID её
владельца; volume также должен быть доступен этому пользователю.

```bash
docker run --rm \
  --network ACCEPTANCE_RDF_NETWORK \
  --user "$(id -u):$(id -g)" \
  --mount type=bind,src="$PWD/acceptance/loader-v2.yaml",dst=/run/secrets/loader_config,readonly \
  --mount type=volume,src=acceptance_loader_state,dst=/var/lib/semantic-bi \
  semantic-bi-loader:feat-loader-contract-v2 \
  --config /run/secrets/loader_config --once
```

Для каждого backend использовать свой конфиг, dataset и volume. Сначала
проверить S3/RDF доступность и права. Код возврата контейнера сохранить, но
оценивать сценарий по объектам S3, графам, checkpoint и `status.json`.

## 4. Порядок базового сквозного прогона

| ID | Действие | Проверка и ожидаемый результат |
| --- | --- | --- |
| E2E-01 | Опубликовать полный snapshot реальным экспортёром v2 | YDB подтверждает новую `epoch_id`; S3 `state.json` каноничен, содержит тот же `revision`, base key/SHA и пустой tip. Все refs читаются и SHA совпадают. `complete_entity_types` соответствует доказанной полноте. |
| E2E-02 | Запустить загрузчик `--once` с пустым checkpoint на каждом backend | Все ожидаемые именованные графы есть, лишних графов нет в тестовом dataset; checkpoint содержит v2 epoch/base SHA, tip пуст; `status.json` показывает `contract_version: 2` и состояние `idle`. |
| E2E-03 | Изменить тестовые deal/user/category `112`/stage/source и опубликовать два последовательных incremental | Манифесты образуют непрерывную цепь `previous_run_id`/`previous_manifest_sha256`; точные `counts` равны числу ссылок соответствующих типов. После загрузки графы соответствуют последним версиям, tip ID/SHA checkpoint равны подтверждённым в `state.json`. |
| E2E-04 | Опубликовать пустой incremental | Появляется подтверждённое звено с нулевыми counts; RDF остаётся тем же, checkpoint перемещается на его ID/SHA. |
| E2E-05 | Повторить тот же запуск загрузчика; отдельно воспроизвести потерю ответа и повтор **того же незавершённого экспортного запуска** | При неизменном подтверждённом state RDF и checkpoint не меняются; повтор экспортёра разрешается чтением YDB/S3 без второго несовместимого манифеста или ложного подтверждения. |
| E2E-06 | Опубликовать manifest backfill и неподтверждённый/failed run вне tip-цепочки; изменить диагностический `status.json` | Загрузчик не применяет эти объекты и не меняет checkpoint. Порядок задаёт только `state.json` и связи подтверждённых манифестов. |
| E2E-07 | Создать новую полную эпоху; изменить/убрать сущность в типе с доказанной полнотой и в неполном типе | Полная сущность, отсутствующая в snapshot, удаляется при разрешённой reconciliation; неполная и `activity` не удаляются по отсутствию. Новый epoch/base SHA фиксируется, старые run ID не смешиваются с новой цепью. |
| E2E-08 | Сделать incremental после новой эпохи | Первый incremental перекрывает `t0` согласно контракту; повторные версии применяются идемпотентно, итоговые RDF и tip совпадают с оракулом. |

Для **каждого** успешного сценария записать: SHA сырого `state.json`, его
revision, base/tip ID и SHA; SHA/тип/число refs каждого манифеста; число
событий и независимо вычисленные event ID; число и список URI графов,
контрольные RDF утверждения; содержимое *несекретных* полей checkpoint/status.
Сравнить полученный RDF с ожидаемым состоянием, а не только с другим RDF,
полученным тем же загрузчиком.

## 5. Негативные сценарии целостности

Каждый сценарий запускать на отдельной копии тестовой цепочки или после
восстановления предыдущего тестового состояния. Снимать checkpoint и RDF
**до** вмешательства и **после** отказа. Если испорченный объект стоит позднее
других событий одного run, ранее применённые события допустимы; обязательные
свойства — сам испорченный event не применяется, run/tip не подтверждается,
а повтор после устранения причины сходится к эталонному RDF.

| ID | Вмешательство | Ожидаемый результат |
| --- | --- | --- |
| INT-01 | Подменить байты объекта категории `112` под ключом, на который ссылается подтверждённый snapshot | Несовпадение SHA блокирует его применение; snapshot/run не считается завершённым. После восстановления исходных байтов повтор приходит к эталону. Если исходные байты восстановить нельзя, готовится новый корректный snapshot/эпоха; SHA checkpoint вручную не менять. |
| INT-02 | Подменить байты подтверждённого manifest или `state.json` при сохранении старых ссылок | Валидация SHA/canonical JSON/структуры блокирует цикл без принятия недостоверной вершины. |
| INT-03 | Удалить/скрыть предшествующий manifest или событие, смоделировав retention gap | Цепочка не перескакивает разрыв; checkpoint не продвигается за него. |
| INT-04 | Подставить manifest с неверным parent SHA, другой эпохой, циклом либо checkpoint, не являющийся предком tip | Цикл блокируется; произвольный manifest из листинга `runs/` не принимается. |
| INT-05 | Попытаться записать другие байты в существующий event/manifest key через реальный S3 endpoint и release identity | `If-None-Match`/bucket policy не допускает смены байтов; конфликт фиксируется экспортёром и не публикует новую вершину. Отдельно проверить запрет безусловного Put тем же identity. |
| INT-06 | Устаревший `If-Match` ETag для `state.json`, конкурирующие писатели и потерянный ответ S3/YDB | Нет регресса revision, подтверждения неверного tip или второго победителя. Экспортёр перечитывает YDB и S3 и продолжает только из подтверждённого состояния. |
| INT-07 | Повторить цикл в `strict` после порчи объекта уже принятого boundary snapshot/run | Порча обнаруживается в пределах гарантий strict. Для более старой истории запустить отдельный пустой checkpoint и полный аудит; `fast` не считать доказательством целостности истории. |
| INT-08 | Нарушить лимит размера state/manifest/event, длины цепи или времени чтения | Цикл останавливается с безопасной диагностикой и без продвижения tip. |

Проверка INT-01 моделирует инцидент с категорией `112`; для отдельной проверки
механизма **предотвращения** такого инцидента нужен INT-05 с реальной политикой
тестового S3. Прямое вмешательство администратора с правом обхода bucket policy
не входит в гарантию экспортёра; загрузчик должен обнаружить изменение байтов
по SHA при чтении затронутого объекта.

## 6. Сбои и восстановление загрузчика

Для каждой точки создать новый тестовый namespace или вернуться к той же
исходной копии. Внедрить однократный отказ в реальной операции/адаптере
(например, proxy, kill/restart, отказ Graph Store или SQLite), сохранить
лог/status/RDF/checkpoint, устранить отказ и повторить **тем же** checkpoint.
Сравнить финальные RDF и checkpoint с эталонным прогоном без отказа.

| ID | Точка отказа | Проверка |
| --- | --- | --- |
| REC-01 | Чтение `state.json` или base manifest | Нет новой принятой epoch/tip; повтор читает те же подтверждённые байты. |
| REC-02 | Обход цепочки или загрузка очередного event | Нет пропуска недочитанного звена; после повтора tip и RDF равны эталону. |
| REC-03 | RDF PUT/DELETE до ответа | Повтор безопасен, один итоговый граф/удаление; checkpoint не опережает RDF. |
| REC-04 | После успешного RDF PUT/DELETE, до записи checkpoint сущности | Та же операция может повториться; RDF и checkpoint сходятся к эталону. |
| REC-05 | После checkpoint сущности, до отметки завершения run | Оставшиеся ссылки обрабатываются; run не считается завершённым преждевременно. |
| REC-06 | Во время snapshot reconciliation после части DELETE | Повтор завершает сверку без удаления типов вне пересечения разрешений и `complete_entity_types`. |
| REC-07 | После подтверждённого YDB CAS, до зеркала S3 `state.json` | Экспортёр восстанавливает зеркало до нового сбора; загрузчик видит только целостную подтверждённую вершину. |

Отдельно проверить backup barrier, `backup verify`, восстановление **пары**
RDF + SQLite в изолированную цель с той же backend/endpoint identity и повторный
цикл. Сравнить графы и tip после восстановления. Для GraphDB учитывать
требования работающего экземпляра и совместимой версии из
[архитектуры backup](BACKUP_RESTORE_ARCHITECTURE.md).

## 7. Несколько потребителей и переход с v1

1. Дать потребителю A дойти до tip, задержать потребителя B на раннем
   checkpoint. Опубликовать ещё два incremental. Оба должны прийти к одним
   графам и tip, каждый через собственную цепочку и checkpoint.
2. Повторить после новой эпохи и на границе retention. Если необходимые B
   объекты недоступны, B должен остановиться и пройти новый полный snapshot;
   пропускать недоступный run нельзя.
3. На **копии** согласованных v1 RDF + SQLite проверить
   `prepare_v2_checkpoint.py`: entity registry сохраняется, старый `last_run_id`
   не становится v2 tip. Применить новую эпоху и сверить графы. В этой же
   копии проверить блокировку v1 checkpoint с v2 state и v2 checkpoint с v1
   state. Не запускать два протокола одновременно против одного RDF/checkpoint.
4. Перечислить всех будущих рабочих загрузчиков, их владельцев, backend,
   checkpoint и ожидаемый максимальный lag. Зафиксировать, кто обновлён до
   совместимого образа, а кто будет остановлен до переключения. Это входной
   шлюз этапа 8, даже если тестовые два потребителя прошли приёмку.

## 8. Артефакты, итоговый отчёт и решение

Для каждой строки матрицы сохранить `PASS` / `FAIL` / `BLOCKED`, дату,
испытанный backend, краткий способ воспроизведения, ожидаемый и фактический
результат, ссылку на очищенные от секретов доказательства и номер дефекта.
Нужны как минимум:

- digest и commit обоих компонентов; обезличенная конфигурация и идентичности
  изолированных S3/YDB/RDF ресурсов;
- журнал S3 условных операций с кодами ответов; проверенные SHA state,
  манифестов и событий; снимки YDB revision и tip;
- независимый расчёт контрольных векторов и таблица ожидаемых/фактических RDF
  графов по типам и ключам;
- checkpoint/status каждого загрузчика после базовых и негативных прогонов,
  результаты backup verify/restore;
- список оставшихся ограничений инфраструктуры и подписанты от экспортёра,
  загрузчика, S3/YDB и RDF.

**PASS для этапа 7**: все обязательные E2E, INT и REC на каждом целевом
backend прошли; после сбоев конечные RDF и `(epoch_id, tip_run_id,
tip_manifest_sha256)` равны эталону; подменённые байты не приняты; реальный
тестовый S3 подтвердил нужные условные операции; backup/restore проверен.
`FAIL` или `BLOCKED` любого обязательного сценария закрывает допуск к этапу 8
для соответствующего backend/конфигурации. Исправление кода, меняющее артефакт,
требует повторить затронутые сценарии и базовый сквозной проход с новым digest.

После PASS подготовить отдельный change record этапа 8: инвентаризация
активных импортёров и писателей, backup рабочего RDF + SQLite, удержание
старых объектов, порядок остановки/публикации нового snapshot/первого
incremental, проверка каждого рабочего tip и правила отката из runbook.

Это изменение фиксирует явное поручение владельца в этой беседе: исключить Fuseki, не проводить перечисленные ниже проверки и оформить принятие остаточного риска. Имя и должность владельца в записи не указаны. Изменяется допустимый итог приёмки; невыполненные сценарии не превращаются в PASS, а ранее записанные доказательства не изменяются.

Для scope GraphDB-only этап 7 может иметь дополнительный итог **ACCEPTED WITH DEVIATIONS**, если владелец принимает указанные ниже исключения. Исходный критерий **PASS** остаётся без изменений и не выполнен. Исключённые сценарии имеют статус `BLOCKED — owner-waived`; дополнительный результат unit suite остаётся `FAIL`.

| Принятое исключение | Статус evidence | Остаточный риск |
|---|---|---|
| Восстановление paired backup, чей checkpoint следует реальной S3-цепочке, затем strict loader catch-up | BLOCKED — исключено владельцем; через внешний KMS bucket восстановлена только synthetic RDF+SQLite пара | Восстановление относительно живой exporter chain и догоняющий цикл после restore не проверены. |
| Миграция согласованной v1 пары RDF+SQLite, применение новой epoch и сверка графа/checkpoint | BLOCKED — исключено владельцем | Поведение migration на сохранённом v1 состоянии потребителя после перехода epoch не проверено. |
| TCP-level неизвестный ответ для YDB CAS/state | BLOCKED — исключено владельцем | Не проверено поведение экспортёра, когда CAS в YDB выполнен, но ответ потерян. |
| Проверка S3 retention/lifecycle и согласование полноты `complete_entity_types` | BLOCKED — исключено владельцем | Не подтверждена доступность звеньев цепи на границе retention; полнота reconciliation независимо не одобрена. |
| Утверждение финальных exporter/loader digests и полная матрица на этой паре | BLOCKED — исключено владельцем | Текущие PASS относятся к зафиксированным кандидатам/артефактам; формально утверждённой финальной пары нет. |
| Operational sign-off / production change record | BLOCKED — исключено владельцем | Нет подтверждения operational readiness, инвентаря активных писателей, cutover процедуры и разрешения отката. |
| Второй новый независимый GraphDB repository | BLOCKED — лимит GraphDB Free | Новый repository A проверен; свежий двух-repository прогон на текущем instance не создан. Исторический multi-consumer PASS остаётся evidence только своего исходного тестового прогона. |

Fuseki исключена из целевого scope, а не считается провалом GraphDB. Дополнительная локальная unit suite `27 PASS / 1 FAIL` (устаревшая дата fixture) остаётся видимой и не переименовывается в PASS.

**Решение по этому amendment:** этап 7 в scope GraphDB-only имеет статус **ACCEPTED WITH DEVIATIONS**; перечисленные исключения и остаточные риски приняты поручением владельца от 2026-11-14. Это не PASS по исходному плану. **Этап 8 остаётся закрытым**: amendment не разрешает production cutover, а operational sign-off исключён владельцем. Для повторного открытия этапа 8 нужны отдельное явное решение владельца и применимый operational change record.
