# План подготовки Semantic_BI к развёртыванию на VPS

Цель — воспроизводимый запуск GraphDB, загрузчика S3 → RDF и монитора из Git на одном Linux VPS с архитектурой amd64. Первичная загрузка начинается с полного базового snapshot контракта S3 v2 и догоняет цепочку инкрементов до вершины, прочитанной в начале цикла. На VPS создаются пустой репозиторий GraphDB и новый SQLite checkpoint.

## 1. Зафиксировать параметры нового стенда

| Параметр | Значение для нового VPS |
| --- | --- |
| GraphDB | Отдельный Compose-проект, образ `ontotext/graphdb:11.5.2` |
| Репозиторий GraphDB | Предлагаемый ID `bitrix24`. Одно значение в инициализаторе, загрузчике и мониторе |
| Правила вывода | OWL 2 RL (`owl2-rl`). Индекс контекстов включён |
| Адрес GraphDB для контейнеров | `http://graphdb:7200` через общую Docker-сеть |
| Источник S3 | Файл [`.env` активной связки `graphdb-v2-parallel-2`](../local-data/remote-graphdb-v2-20261115/graphdb-v2-parallel-2/.env) |
| Начальное состояние загрузчика | Отдельный пустой том, `/var/lib/semantic-bi/state.sqlite3`, режим `strict` |
| Статус монитора | `/var/lib/semantic-bi/status.json` из того же тома, подключённого к монитору для чтения |
| Доступ снаружи | Порты GraphDB и монитора привязаны к localhost VPS. Для просмотра используется SSH-туннель |

В качестве ориентира для общего тестового VPS использовать 4 vCPU, 8 ГБ RAM и около 100 ГБ SSD. Диск уточнить по размеру графов и резервных копий. Лимит GraphDB — одно ядро в соответствии с лицензией.

## 2. Подготовить изменения в Git

1. Актуализировать ветку относительно удалённой целевой ветки. На момент подготовки плана локальная ветка `docs/multi-station-loader-v2` опережает локальную ссылку `origin/main` на четыре коммита. Пять новых файлов GraphDB пока отображаются как untracked.
2. Включить в коммит `deploy/graphdb/compose.vps.yaml`, `create-repository.sh`, `repository.vps.template.ttl`, `.env.vps.example`, `VPS.md` и этот план. Добавить в README один рекомендуемый маршрут для чистого развёртывания на VPS.
3. Использовать `deploy/graphdb/compose.yaml` как основу для второго Compose-проекта с загрузчиком, монитором и профилем резервного копирования. Сделать пути к YAML загрузчика и env монитора параметрами Compose с сохранением текущих значений по умолчанию. Подключить оба сервиса к той же внешней сети, которую использует GraphDB. Для VPS выбрать отдельное имя тома checkpoint и документировать его создание и назначение прав на запись для `LOADER_UID:LOADER_GID`. Зафиксировать имена двух Compose-проектов для повторных запусков. Вариант из активной локальной установки использует host networking и для этого сценария требует замены адреса на `http://graphdb:7200`.
4. Добавить обезличенные шаблоны настроек VPS для загрузчика и монитора. В инструкции явно связать ID репозитория, S3 bucket и portal ID между шаблонами. Проверить правила игнорирования рабочего `.env.vps` и лицензионных файлов. Рабочие конфиги, SQLite, резервные копии и файлы из `local-data/` хранить вне Git. Для VPS удобно использовать каталог конфигурации вне checkout.
5. Уточнить поведение сервиса `repository-init`. Он должен дождаться API с ограниченным временем ожидания и завершиться успешно после создания репозитория. При повторном запуске он должен подтвердить, что существующий репозиторий использует `owl2-rl` и индекс контекстов. Несовпадение должно завершать подготовку с ошибкой и понятным сообщением без правки репозитория. Проверить очистку временных файлов, обработку ответов API и доступ пользователя контейнера GraphDB к лицензии.
6. Использовать публичный release wheel `cccr_py` с URL и SHA-256 в `uv.lock`. Не включать исходники CCCR в checkout или Docker build. Удалить SourceCraft credentials, submodule и `auditwheel`-сборку. Проверить импорт wheel и loader tests в чистом runtime image.
7. Выполнить проверки Compose и smoke запуск на отдельном стенде. Проверить чистую и повторную инициализацию GraphDB, доступ к API из Docker-сети, чтение статуса монитором и сборку образа в CI. После ревью опубликовать фиксированный тег loader и monitor и подтвердить доступность обоих образов в GHCR. `v2.0.1` — версия действующей локальной связки. Её можно использовать для первого запуска после успешного скачивания обоих образов с VPS. Для релиза с изменениями кода загрузчика выбрать новый тег и связать его с коммитом.

## 3. Подготовить и передать закрытый конфигурационный bundle

Выполняйте подготовку на доверенной рабочей машине, а не в Git checkout на VPS. [Runbook для Codex CLI](../deploy/graphdb/VPS.md) задаёт полный порядок действий агента на сервере. Генератор `scripts/prepare_vps_bundle.py` читает источник S3-настроек [активной связки `graphdb-v2-parallel-2`](../local-data/remote-graphdb-v2-20261115/graphdb-v2-parallel-2/.env), обезличенные шаблоны, лицензию и отдельный Docker auth config; он сверяет несекретные настройки и записывает готовые конфиги с секретами в архив вне checkout с режимом `600`.

Docker auth config должен быть создан Docker CLI на доверенной машине с PAT classic и `read:packages`. В bundle включается только секция `ghcr.io`; auth config содержит обратимо закодированные credentials, поэтому архив и конфигурация считаются секретами. Передавайте архив на VPS по SSH отдельно от Git. Не выводите его содержимое и не помещайте распакованные файлы в Git.

```sh
python3 scripts/prepare_vps_bundle.py \
  --license-file /path/to/graphdb.license \
  --docker-config /path/to/ghcr-config/config.json \
  --image-tag v2.0.1 \
  --output /tmp/semantic-bi-vps-configs.tar.gz
scp /tmp/semantic-bi-vps-configs.tar.gz deploy@VPS:/tmp/semantic-bi-vps-configs.tar.gz
```

Скрипт использует `S3_BUCKET`, `S3_PORTAL_ID`, `S3_ENDPOINT_URL`, `S3_REGION`, `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`. Значения не печатаются и не записываются в отслеживаемые файлы; локальный рабочий `.env` не меняется. Получатель устанавливает файлы вне checkout в `/etc/semantic-bi` с правами из runbook.

Для соответствия полей в итоговых конфигурациях:

| Поле текущего `.env` | Поле `loader.yaml` |
| --- | --- |
| `S3_BUCKET` | `s3.bucket` |
| `S3_PORTAL_ID` | `s3.portal_id` |
| `S3_ENDPOINT_URL` | `s3.endpoint_url` |
| `S3_REGION` | `s3.region` |
| `AWS_ACCESS_KEY_ID` | `s3.access_key` |
| `AWS_SECRET_ACCESS_KEY` | `s3.secret_key` |

Локальные `state/`, SQLite-файлы и резервные копии исходной GraphDB остаются на исходной машине. Если на VPS уже есть том checkpoint или репозиторий с данными, выделить новые ресурсы для чистой установки.

## 4. Развернуть через Codex CLI и принять стенд

Запустите Codex CLI на VPS из deployment checkout и поручите ему выполнить [runbook](../deploy/graphdb/VPS.md). Инструкция содержит проверяемые пред-условия, конкретные команды Compose, проверку безопасного состава bundle, назначения владельцев/прав, создание новых пустых томов, двукратный запуск GraphDB repository initializer, сетевую проверку и первый strict `--once` цикл. После отчёта первого цикла агент обязан остановиться и дождаться явной приёмки оператора до запуска фоновых loader и monitor.

На VPS Docker CLI получает переданный `docker-config/config.json` через `DOCKER_CONFIG` и скачивает образы. Ручной `docker login` на VPS не требуется. GitHub Actions публикует образы с `GITHUB_TOKEN` и разрешением `packages: write`; PAT `read:packages` используется только при создании переносимого auth config на доверенной рабочей машине. [Документация GHCR](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).

## 5. Критерии готовности

Проверки и точные команды выполняет Codex CLI по [runbook на VPS](../deploy/graphdb/VPS.md). До приёмки должны быть подтверждены: оба приватных образа скачиваются; Compose-конфигурации валидны; checkpoint volume пустой и доступен UID `10001`; GraphDB принимает лицензию и два последовательных запуска initializer завершаются успешно; repository `bitrix24` пуст, имеет `owl2-rl` и включённый context index; loader достигает GraphDB по `http://graphdb:7200`; первый strict `--once` цикл успешно прочитал базовый snapshot v2 и догнал доступные инкременты.

После отчёта по первому циклу оператор принимает результат. Только после явной приёмки Codex CLI запускает постоянный loader и monitor. При ошибке любого этапа агент прекращает зависимые действия, сохраняет данные для диагностики и сообщает точный шаг, код выхода и безопасные сведения из логов. Локальные RDF-данные и SQLite checkpoint не копируются на VPS.

## Результат подготовки в рабочей копии

- Добавлен VPS-маршрут с двумя именованными Compose-проектами, отдельными томами, сетью GraphDB, конфигами вне checkout, первым `--once` strict циклом и последующим запуском фоновых сервисов. Прежнее имя GraphDB data volume и checkpoint volume остаются значениями по умолчанию; smoke использует настраиваемое имя GraphDB data volume.
- Инициализатор ограничивает ожидание API, создаёт отсутствующий repository и подтверждает `owl2-rl` с включённым context index. Несоответствие существующей конфигурации приводит к ошибке без изменения repository.
- Несекретные bucket, portal ID, endpoint и region из локального `.env` согласованы с шаблонами. Генератор читает access key и secret key только для включения в закрытый архив вне checkout; он не печатает их и не записывает в отслеживаемые файлы. Локальный `.env` не изменялся.
- Старый gitlink `7c5b5116d0b178a6d315b639762602364c49365a` недоступен с публичного GitHub URL. Release `v0.1.0` содержит готовые cp310–cp313 wheels; cp313 wheel закреплён URL и SHA-256 в `uv.lock`. Его установка и `import cccr_py` проверены на `python:3.13.9-slim-trixie`. Loader Dockerfile успешно собрался без native build и `auditwheel`, импортировал `cccr_py`, выполнил все 25 loader tests; runtime image также прошёл `--help`. Исходный submodule и скрипт native-сборки удалены; оба workflow используют готовый wheel без SourceCraft.
- Изолированный GraphDB smoke прошёл: repository `bitrix24` создан с `owl2-rl` и `enableContextIndex=true`; повторный запуск подтвердил идемпотентность. Peer-контейнер получил доступ к REST API по `http://graphdb:7200`. Дополнительный repository с `rdfs` остался неизменным после отказа инициализатора. Для GraphDB 11.5 исправлены JSON-проверка REST-конфигурации и имя параметра `enable-context-index` в Turtle шаблоне. Изолированные контейнеры, сеть и том после проверки удалены. S3 импорт на этом окружении не выполнялся.
- Сценарий использования опубликованных GHCR тегов и S3 полного импорта остаётся VPS-проверкой. Новые образы не опубликованы. Для передачи готовых конфигов добавлен `scripts/prepare_vps_bundle.py`; создаваемый секретный архив по умолчанию находится в `/tmp/semantic-bi-vps-configs.tar.gz` и не входит в репозиторий.
