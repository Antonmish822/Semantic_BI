# Следующий этап: надёжность очереди синхронизации

Этот список фиксирует подтверждённые по текущему коду проблемы протокола между `bitrix24_s3_export` и S3→Fuseki-синхронизатором. Это задачи на следующий этап; текущий документ не означает, что изменения уже внесены в код.

## Задача 1. Унифицировать порядок и формат run ID

**Наблюдение:** обычные incremental запуски получают ID с UTC timestamp в начале (`YYYYMMDDTHHMMSSZ-...`). Сценарий `operations/refresh.py` назначает catch-up запуску ID `refresh-catchup-<timestamp>`. Синхронизатор сравнивает ID лексикографически для границ и вызывает `run_id_time()` по первым 16 символам. После успешного catch-up checkpoint ID может лексикографически опережать следующий обычный run; парсер времени для него возвращает `None`.

**Последствие:** следующая регулярная синхронизация может завершиться ошибкой, что checkpoint «опережает» exporter `state.json`, и не выбрать новые timestamp-prefixed манифесты.

**Направление решения:** определить единый упорядочиваемый идентификатор для всех incremental runs, включая ручной catch-up. Альтернативно — перестать использовать строковое сравнение ID для временного порядка, перейти на `window.to`/`created_at` и хранить курсор в нормализованном временном представлении. Не менять поведение до согласования одного порядка для exporter и consumer.

**Критерии приёмки:**

- последовательность `обычный incremental → refresh snapshot → catch-up → следующий обычный incremental` обрабатывается без отката/ошибки;
- catch-up и обычные runs имеют однозначный порядок при одинаковых временных границах;
- восстановление exporter state и SQLite checkpoint проверяется тестами на старые и новые ID;
- retention/85-дневная проверка работает для всех поддерживаемых типов run ID.

## Задача 2. Восстановление после manifest с failed/missing status

**Наблюдение:** exporter публикует `manifest.json`, затем для incremental фиксирует внутренние курсоры и обновляет S3 `state.json`, а `status.json` пишет в блоке `finally`. Сбой после публикации manifest может оставить его видимым со статусом `failed` или без status marker. Синхронизатор требует успешный status marker и при неуспехе останавливает обработку на этом run, откладывая все последующие. Он не пытается повторно вызвать exporter для того же run и не имеет отдельной процедуры разрешения poison run.

**Последствие:** один прерванный запуск способен остановить обработку более новых завершённых инкрементов. Простое пропускание run небезопасно: его события могли быть единственной доставкой изменений.

**Направление решения:** согласовать протокол завершения exporter/consumer так, чтобы manifest, cursor state и status marker имели однозначную семантику при сбое. Определить, как можно повторно материализовать или подтвердить run без потери изменений и без продвижения через неполный run. Не считать отсутствующий `status.json` успешным и не пропускать failed run без доказательства полноты данных.

**Критерии приёмки:**

- смоделированы сбои до manifest, после manifest, после внутреннего cursor commit, после `state.json` и при записи `status.json`;
- повторный запуск безопасно восстанавливает незавершённый run либо явно переводит систему в диагностируемое состояние с инструкцией восстановления;
- более поздние runs не применяются с потерей порядка или пропуском событий;
- тесты покрывают failed и missing status, включая восстановление после перезапуска consumer-а.
